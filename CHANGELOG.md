## [13.1.2]

### Added
- **A shop can be pinned to a map** (`scripts/utility-pins.js`, `scripts/manager-merchant.js`). *Pin This Shop* sits in the shop window's header and in Merchant Settings; double-clicking the pin opens the shop, the same window and the same cart a token would. **Only a linked merchant may be pinned** — a pin outlives tokens, scenes and sessions, so what it names has to outlive them too, and an unlinked token is a copy: pinning one would name the mould rather than a shop. One pin per shop per scene; a second is two doors onto one room with nothing to tell them apart. Built on Blacksmith's pins API, which owns the rendering, the dragging, the config window and the layer — what is ours is which Actor a pin names and what a click does.
- **A pin whose merchant is gone opens an abandoned shop** (`templates/window-shop.hbs`, `styles/window-shop.css`). Shutters down, shelves bare, nobody behind the counter, under the name the pin remembers. The pin is deliberately **not** deleted — removing a GM's map furniture unasked is the same failure as a roll table's dead row vanishing — and a shop closing down is a thing that happens in a world, where a line of apology in an empty window is a thing that happens to software.
- **A *Shop Pins* section in the settings** (`scripts/const.js`, `scripts/settings.js`): shape, size, background, border, icon colour, and whether the name shows. The **icon is deliberately not settable** — it comes from the shop's kind, so an apothecary and a weaponsmith are told apart on the map without anybody configuring anything. Blacksmith's own per-user *Default for [type]* design wins over the world's where a GM has saved one, because they took the trouble; neither reaches a pin already placed, which keeps the look it was made with.
- **The world's stocking limits are shown as a table** on the Inventories card (`templates/window-merchant-config.hbs`, `scripts/window-merchant-config.js`). Read-only on purpose — they are world settings, and a control here would be a second place to set one thing. Two tables rather than four columns of one, because a type ceiling and a rarity ceiling are separate rules that happen to share a unit. A limit of 0 reads **No limit**, which is the one thing the numbers alone cannot say.
- **A play button beside each sound setting** (`scripts/settings.js`, `scripts/utility-feedback.js`). Choosing a sound you cannot hear is choosing blind: six dropdowns of file names is a list of guesses, and the alternative — save it, then trigger the thing in play to find out — is a slow way to audition forty files. It plays **what the dropdown currently says**, not what is saved, because a GM scrolling the list wants to hear the one under the cursor. Disabled on *none*, since a button that silently does nothing reads as broken. Injected on `renderSettingsConfig` and appended into the existing field cell rather than rebuilding the row — reimplementing in CSS what Foundry already renders is the mistake `api-toast` records making.
- **A compendium on a shelf's list can be switched off without being removed** (`scripts/utility-compendium.js`, `scripts/manager-merchant.js`), the same gesture the roll tables beside it already had and for the same reason: a seasonal pack, or one a GM is trying out, should not have to be taken off and re-dropped. Entries are `{ id, enabled }`; a bare id reads as enabled, because that is what a list written before the switch existed meant. A shelf whose every pack is switched off draws nothing and says so, exactly like an empty list.
- **A two-source shelf says which half draws first** (`scripts/const.js`, `scripts/manager-merchant.js`). *Roll Tables First, Item Compendiums Second* and *Item Compendiums First, Roll Tables Second* are now separate choices. Both halves feed one product target, so on a nearly full shelf whichever runs first gets the last slots — the whole difference between a shop stocked from a list somebody wrote and one stocked from whatever happens to be installed. That was fixed at tables-first with the reasoning in a comment; a fence and a general store want opposite answers.
- **Inventories can be moved up and down** (`scripts/manager-merchant.js`, `templates/window-merchant-config.hbs`). Order is the shop's layout — what is on the counter and what is in the back room — and it was whatever order the containers happened to be created in. A move renumbers **every** inventory rather than swapping the pair: they start life sharing an order of 0, so swapping two zeroes would move nothing, and writing the whole sequence also repairs a shop whose numbers were never set. Hidden inventories are included, or a move would jump two places whenever one sat between. One write for the shop.
- **A shelf can draw from its own list of compendiums** (`scripts/utility-compendium.js`, `scripts/manager-merchant.js`, `scripts/window-merchant-config.js`). **Curated or custom, never both.** The curated set — the Item packs configured in Blacksmith — is the world's answer to *what content do we use*, and every Coffee Pub module matches against it; a shop reaching outside it is saying something different rather than something extra, and a fence drawing on a pack of cursed junk is not asking for that pack to join the world's item matching. Packs are **dragged on**, like the roll tables beside them: a compendium from the sidebar, or any document out of one, because finding the pack you want by finding a thing in it is how anybody browses. Dropping the first pack switches the shelf off the curated set — a GM dragging a pack has already said which packs they mean.
- **An empty custom list draws nothing, and says so.** Three stored states, not two: `null` is the curated set, an array is this shelf's list, and `[]` is a list nobody has filled yet. Falling back to curated on the empty case would restock a shady fence from the world's ordinary content the moment its last pack came off — emptying a list is not the same gesture as abandoning it. A restock in that state names the reason rather than reporting an empty query.
- **A pack outside the curated set is marked *Waiting*, not silently dropped.** `compendiums.query` filters a requested source against the curated set, so it can only narrow — a shelf naming an uncurated pack would get a plausible result set drawn from the wrong content. The row says why on hover, and a list whose every pack is uncurated refuses the draw outright. Recorded as a seam in the architecture doc with what to delete when the hub honours them.

### Changed
- **A shop is now identified by what it durably *is*: the Actor for a linked merchant, the token for an unlinked one** (`scripts/window-shop.js`, `scripts/manager-merchant.js`). The window registry keys on the uuid it is handed, so this is the whole mechanism — and it fixes something latent: two placed linked tokens of one Actor used to open two windows with two separate carts for what is, by every other measure, one shop. It is also what lets a pin and a token be one door onto one shop. `_resolveToken()` becomes `_resolveSubject()`, returning `{ actor, token, scene }`, where **the token may be null and the Actor may not**.
- **The scene a shop is priced in is carried explicitly**, because it cannot be derived from an Actor. The market rate and the party's standing are both scene-scoped, so one linked merchant with a token in one town and a presence in another is one shop with one set of goods at two prices — the trade route working as designed. A client-supplied scene is a **claim**: `verifiedScene` honours it only where a token of that merchant actually stands, since an unchecked one would let a client price itself into a favourable market.
- **A linked merchant opens as a shop with no token placed anywhere** (`scripts/manager-merchant.js`, `scripts/window-merchant-config.js`). *Open shop* used to hunt the current scene and then every other one for a token, and gave up if it found none — true when a token was the only door. An unlinked merchant still needs its token, because there the token *is* the shop.
- **A shop has a voice out of the box** (`scripts/settings.js`). The six sounds defaulted to silence, on the argument that a module making noises nobody asked for is a module people turn off — true of a module that decides *when* to speak, and this one only ever speaks because a person just did something. Silence made the feature look broken instead: a GM who never opens the settings tab never hears the counter at all, and one who does has forty file names to audition before knowing what the module sounds like. Every default is a Blacksmith sound, so nothing ships here, and *None* is one click away on any row.
- **The settings tab is laid out like the rest of the suite** (`scripts/settings.js`). Blacksmith's `settings.css` styles any setting keyed `headingH1`–`headingH4` in a `coffee-pub-*` module as a section header — Squire and Blacksmith both use it, and Merchant was the odd one out, registering eighteen flat rows with no structure. It now reads **Merchant → Stock Depth (By Item Type, By Rarity) → Sound**. The trick is that a setting is the only thing Foundry renders in that list, so a header has to be one: the stored value is an empty string nobody reads.
- **The stock ceilings carry no per-setting hint.** Thirteen rows each re-teaching the same model — *the most of one X a shop stocks at once, 0 means no limit* — is harder to scan than thirteen labelled sliders, and it buried the one thing a reader must be told: `Common: 0` means *no limit from rarity*, not *no common items*. The system is explained once in the section headings, where it stays visible while the sliders are read. Explain the system at the section level; label the controls at the control level.
- **The twelve stock ceilings are sliders** (`scripts/const.js`, `scripts/settings.js`). Each is a small integer with a floor, a ceiling and no meaningful decimal, which is what a slider is for and what the suite uses for the same shape of answer. A bare number field invites 250 into a question whose largest sensible answer is a dozen, and reads as though it wanted one. `MAX_STOCK_CAP` is 20 — past that a ceiling caps nothing a shop would draw, and a slider whose useful travel is its first tenth is a number box with a worse hit area.
- **The note at the foot of Item filters was two notes, and neither was about filters** (`templates/window-merchant-config.hbs`, `lang/en.json`). One half described the compendium source — *drawn from what is installed right now* — and now sits under the Compendiums list it is about. The other described what a restock does — *existing rows are topped up first; a draw only brings in things the shelf does not already carry* — and now sits in Inventory restocking beside the controls that say when, where it is also true of a table-stocked shelf rather than only a compendium one.
- **A shelf's Item filters now apply to roll-table draws as well as to compendium ones** (`scripts/utility-compendium.js`, `scripts/manager-merchant.js`, `templates/window-merchant-config.hbs`). They only ever filtered the query, so a shelf that deals in consumables under 50 gp dealt in them or not depending on which source happened to fetch the thing — the shelf's own description came apart along a seam the GM cannot see. `matchesFilter` asks the same question of a resolved document that Blacksmith asks of the index, and the filters group is shown for any shelf that draws rather than only for a query shelf. A table entry that fails is reported apart from a dead row: the table is fine, the shelf simply does not carry that.
- **Unpriced items pass a price filter that is not filtering on price.** With the range wide open (0 to Any), dropping a GM's unpriced trinket would be a refusal nobody asked for; once a range is stated, a thing with no price is outside it. The compendium half cannot make that distinction — unpriced and free share a stored 0 at the index — which is why it excludes unpriced outright and this does not.
- **A drop target now looks like it will catch the thing** (`styles/window-merchant-config.css`, `styles/window-shop.css`). The only signal was a one-pixel dashed rule changing hue — a difference you have to go looking for, while you are looking at the cursor and the drag preview under it. The border is 2px and goes solid on hover, and the ground takes a wash of the interactive colour. Kept to a wash: the point is *this one*, not a colour field the label has to survive. Same treatment on the shop window's inventory and cart targets.
- **Hover is the house orange, in both windows** (`styles/common.css` and both window sheets). Every hover and drop-target highlight used `--blacksmith-tool-accent`, which under the Light theme resolves to the same near-black the section headings use — so a hovered control looked exactly like an un-hovered heading, and nothing said *this responds to you*. Orange is what Blacksmith's own titlebar and menubar use for the same job: it reads on all three themes without a per-theme value, and it means the same thing in every Coffee Pub window. Named once as `--merchant-interactive` in `common.css`, so both windows say it the same way and the day the hub exports a token there is one line to change.
- **The curated set is named, not just described** (`scripts/window-merchant-config.js`). The hint said the shelf draws from “the item compendiums configured in Blacksmith”, which is a place to go and look; it now lists them. A world with none configured is told that, rather than left to wonder why a shelf set to curated draws nothing.
- **The Item source heading no longer has a “Source” label under it** (`templates/window-merchant-config.hbs`). It was the only control in the group, so the label repeated its own heading; the picker takes the full width instead.
- **A card's group headings were being styled by Foundry, not by us** (`styles/window-merchant-config.css`). Foundry and dnd5e style bare `h4` with their own family and `font-variant: small-caps`; a class rule wins on specificity only for the properties it *declares* and silently inherits the rest, so ours set a size and a colour and left the family and the small-caps to somebody else — which is why a section heading rendered as a small-caps serif label smaller than the field labels beneath it. Every inherited heading property is now stated. Sized at .86rem, above the .72rem field labels and below the section heading.
- **The group headings inside an inventory card read as headings** (`styles/window-merchant-config.css`). They were wearing the shop window's *category* treatment — .62rem, muted, letterspaced, uppercase — which is right over WEAPON and CONSUMABLE, where the word names a kind of thing and should recede behind the rows beneath it. Here the word names a decision the GM is about to make, and four of them stacked down a card at that size read as small print rather than as the structure of the card. Now sentence case at .78rem in the card's own text colour: clearly under the section heading above, clearly over the field labels below. The rule and the spacing were already doing the separating; the shouting was carrying none of it.
- **The shelves are cards beside the Inventories card, not inside it** (`templates/window-merchant-config.hbs`, `styles/window-merchant-config.css`). The nesting said nothing the position does not: a card in a card bought a second border, a second background and eleven pixels of indent, and paid for them with the width every row inside had to fit in. The Inventories card keeps the heading, the add button, the count and the world-settings summary — the things that are about the set rather than about one shelf.
- **The inventory card is ordered the way a GM thinks** (`templates/window-merchant-config.hbs`): **Item Source** → **Item Filters** → **Inventory Configuration** → **Inventory Restocking**. It used to run configuration and restocking *before* the source and its filters — asking how deep a shelf stacks and how often it refills before saying what is on it at all.
- **The source menu says what each choice does**, in narrowing order: *Manual Only — Drag Items to Stock*, *Item Compendiums*, *Roll Tables*, then the two orderings of both. The compendium modes are *Curated Blacksmith Compendiums* and *Manually Selected Compendiums*, which name where the packs come from rather than describing the mechanism.
- **“Configured Compendiums” is now “Curated Compendiums”** (`lang/en.json`), in the source picker and on the card. *Configured* describes the mechanism; *curated* describes what the set means — the content this world has agreed to use — which is the distinction the shelf's own list now hangs on. The filter group beneath it is *What To Draw*, since *Which Compendiums* is a separate question sitting above it.
- **`documentation/TODO.md` is what is open, ranked, and nothing else.** It had grown a second job: eleven engineering rules under *Standing rules — inherited lessons*, five of which also appeared verbatim two sections above under *Nits and known gaps*, plus an empty *Couplings and gaps* heading. Those rules already had a home — `CONTRIBUTING.md` carried most of them — so the file now opens with a **ranked rollup table** and carries six detailed entries behind it, each with a category, a size and what it is waiting on. The three rules that were genuinely missing moved to `CONTRIBUTING.md` as §9 (nothing reads `game` at module scope) and §10 (the two Blacksmith traps that look like success), and the expiry rule now carries the incident that earned it.
- **Five dangling documentation pointers fixed.** `CONTRIBUTING.md` opened by telling the reader to go and read a TODO section that is now in `CONTRIBUTING.md`; §9 cited `plan-extraction.md`, which does not exist; the architecture doc and `DECISIONS-TO-REVIEW.md` both pointed at *Inherited lessons*; and `README.md` still listed `documentation/plans/` and claimed **No localisation** under Known gaps, 330 keys after that stopped being true.

## [13.1.0] - 2026-08-24

### Added
- **Stock rows show rarity beside the kind** (`scripts/const.js`, `templates/partial-shop-row.hbs`), on both sides of the counter — what the party is trying to hand over is where the difference between a rare one and a plain one is the whole conversation. In the colours everyone at the table already reads without being told, mixed toward the theme's own text colour rather than set flat: a green dark enough to read on parchment disappears on the dark theme, and this window runs in three. **A blank rarity shows nothing rather than “Mundane”** — dnd5e leaves `system.rarity` empty on everything non-magical, so most of a shop has none, and spending the line on rope and torches is spending it on the rows that need it least. Rarity also joins the search key, so *rare* finds the things worth asking about.
- `itemRarity` and `rarityLabel` (`scripts/const.js`) are now the one place either is derived. The query filter's chips had their own copy of the token-to-words rule and were one edit from disagreeing with the row about the same six words. Blank-is-not-`common` is pinned in `tests/test-actions.mjs` — the same conflation that once capped every torch in the world at the common-magic-item ceiling.
- **A shop can carry a colour** (`scripts/const.js`, `scripts/window-merchant-config.js`, `styles/window-shop.css`). A colour picker **on the end of the Shop Illustration row** — the same question about the same card, where a row of its own said it was a third thing — washes the shop card in a colour of the GM's choosing — a smithy red, an apothecary green, whatever this table has agreed the colours mean. Deliberately the GM's to set rather than derived from the shop kind: a tint taken from the kind would say what Merchant thinks the shop is, where a GM colour-coding by district, by faction or by who owes them money is doing something a fixed palette cannot. Three controls on one value — a hex box that can say *none*, a swatch that opens on the card's own leather rather than on a black nobody chose, and a cross to clear it.
- The wash is **additive**, so a shop with no tint renders exactly the card it always did, and it layers correctly over an illustration: picture, then the veil that seats light text on it, then the colour, lighter there than on a plain card because a photograph carries its own. Mixed against `transparent` rather than into the surface — `color-mix` with an `rgba` adds the two alphas, so a tint would have quietly darkened the card as well as colouring it, and every colour picked would have made the veil heavier.
- **The tint is validated as a hex colour on the way in and again on the way out** (`normalizeTint`). It ends up inside an inline `style` attribute, and a flag is something a GM can hand-edit and a macro can write, so `#c33` and `#cc3333` become one lowercase six-digit form and everything else — a colour name, a typo, a colour with more CSS after it — becomes no tint at all. Pinned in `tests/test-actions.mjs`.
- **Duplicate rows can be folded together** (`scripts/manager-merchant.js`, `scripts/window-shop.js`). A tidy button on the inventory header merges rows that are the same thing — matched on name and kind, quantities added up, the first row the survivor so the shelf keeps its order. **Nothing makes these any more**: a draw skips whatever the shelf already carries. But nothing removed them either — a restock only tops rows up to their level — so pairs made before that rule existed sat there indefinitely, and this is the only way to clear them. The merged row keeps the **highest** level of the group and is not raised to the total: what a shelf is kept at is a decision about the shop, not the sum of three accidents of history, so the surplus sells through like any other over-stocked row. A GM presses it rather than it happening to them, because matching on name and kind is approximately right and two rows might have been kept apart on purpose.
- **The restock button is only on shelves that can restock** (`scripts/manager-merchant.js`, `templates/window-shop.hbs`). `canRestock` decides it, and it is deliberately not the clock's test: a table with its automatic switch off is skipped by the clock but is exactly what the button is for. What it removes is the dead ends — a buyback shelf, which holds what the party sold and has no level to return to, and a hand-stocked shelf that is not set to restock, which has nothing to refill *to* and no source to draw from. Both could only ever report “nothing to restock”, and a control that never does anything reads as broken rather than as absent.
- **The shop’s stock can be sorted by name or by price** (`scripts/window-shop.js`), from an icon beside the search box. **Within each category, never across it** — the grouping is the coarse answer and this is the fine one; sorting a whole inventory would throw away the kinds that make forty rows readable. Two orders rather than the sell side’s three: a category *is* the grouping, so a “by kind” order would answer a question the layout already has. Name is the default, because that is how somebody looks for a thing they came in for. An unpriced row sorts last either way — “no price” is not a number, and at either end of one it would read as free or as priceless, and it is neither.
- **A search opens any folded shelf holding a result** (`scripts/window-shop.js`, `styles/window-shop.css`). A folded shelf that hid a match would make the search lie — worse than finding nothing, because an empty result reads as an answer. The fold is a decision somebody made, so the search lays a second class over it for as long as it lasts and never rewrites it: clearing the box puts every fold straight back. The chevron follows what is on screen rather than what was chosen, so it never points shut over an open list.
- **Inventories fold away** (`scripts/window-shop.js`, `templates/window-shop.hbs`). Click a shelf’s name to shut it; click again to open it. A shop with six inventories was six lists whether or not you wanted them. **The name is the control, not the heading** — a click target spanning the row would fold the shelf every time somebody missed the restock icon. Folding is a view preference and is never written to a document: two people at one counter can have different sections shut, and a GM tidying their own view does not reach into what a player sees. Kept per token, so closing the shop and reopening it finds it as you left it — the promise the search box and the scroll positions already make. A folded shelf keeps its count badge and its controls, so it still says how much is in it and can still be restocked.
- **A shop can have an illustration** (`scripts/const.js`, `scripts/window-merchant-config.js`, `templates/window-shop.hbs`). A **Shop illustration** field under Shop name, browsable or typed, shown as a backdrop behind the shop card. The portrait is who is behind the counter; the illustration is what the place looks like — different questions, stored separately. It renders beneath the card at low opacity with a gradient over the text edge, so every word stays where it was and a shop without one renders exactly the markup it always did.
- **Clicking the portrait changes it**, and the prototype token with it — a shopkeeper whose sheet and token disagree is two characters as far as the table is concerned. Placed tokens are left alone: changing art under a player mid-scene is a different act from setting a merchant up.
- **A fourth stock source: *Roll Tables, then Configured Compendiums*** (`scripts/const.js`, `scripts/manager-merchant.js`). What a real shop is — a few things that make it *this* shop, and a lot of ordinary stock nobody chose individually. Both feed one product target, so the order matters: **tables take the free slots first**, because somebody wrote that list and the query is filler. Nothing arrives twice — the draw already matches rows by name and type, so the same longsword from both sources is one row. The card shows the table list *and* the filter rather than a third arrangement.
- **A third stock source: Manual** (`scripts/const.js`, `scripts/manager-merchant.js`). *Nothing — stocked by hand.* A restock still tops its rows up to their quantity; what it never does is bring in something the GM did not put there. That is a different statement from a table shelf that happens to have no tables on it, and it is the one a curated shelf — a fence's shady goods, a smith's one good blade — actually wants to make.
- **An inventory can stock itself from the compendiums instead of a roll table** (`scripts/utility-compendium.js`, `scripts/manager-merchant.js`, `scripts/window-merchant-config.js`). Each inventory picks a **Source** — roll tables, or the compendiums — and a query shelf says what the shop deals in: which kinds, which rarities, what price window in gold. It draws from what is installed at the moment it runs, so it never goes stale and picks up new content on its own, where a table stores references that dangle when a pack is renamed or a module uninstalled. Built on Blacksmith's `compendiums.query`, which owns the three dnd5e facts that are each a silent wrong answer rather than an error: mundane gear has a **blank** rarity rather than `common`, prices carry a denomination so 50 sp is 5 gp, and unpriced and free share a stored 0 and cannot be told apart. Feature-detected rather than version-pinned — on an older Blacksmith the card says so and the shelf falls back to its tables.
- Candidates are **over-fetched and shuffled** (Fisher-Yates, not a comparator returning random signs, which is not a shuffle). The query answers in scan order, so taking the first N would give every shop in the world the same opening inventory from the same pack.

### Changed
- **One table can be rolled up to fifty times, not twenty** (`scripts/const.js`, `scripts/manager-merchant.js`). The old ceiling was set when a shelf carried twenty-five products, and it bit harder than it looked: a draw brings *new products only* and coalesces repeats within itself, so twenty rolls on a thirty-row table yields well under twenty rows — a single-table shelf could not reach a target of fifty and had no way to ask. `MAX_TABLE_ROLLS` now matches `DEFAULT_MAX_PRODUCTS`, because the two are the same question from opposite ends. Not higher: each roll is its own await, and a ceiling nobody will use invites a mistyped 90.
- **Blacksmith is pinned to 13.19.2**, up from 13.19.0 (`module.json`, `scripts/merchant.js`, `README.md`). The compendium-stocked shelves and the “Buying as” picker run on `compendiums.query` and `dialog.pickActor`, neither of which exists before that. The query half feature-detects and falls back to roll tables, so on an older hub it fails *quietly* — which is the worse failure for a first run, and the reason the manifest states it rather than leaving it to be discovered.
- **The architecture document is current again** (`documentation/architecture/architecture-merchant.md`). It described the illustration as a `::before` at low opacity — the treatment that was rejected — and still claimed a schema pass stamped par onto old rows, after every migration was deleted. It now also covers the four stock sources, `canRestock`, folding duplicate rows, the tint, and the shop window's folds, sort and rarity.
- **Trading hours answer beside the track**, like every other slider in Merchant Settings (`templates/window-merchant-config.hbs`). It was the odd one out: the markup rates and the price range each put their current value in a badge at the end of the track, where the eye lands after dragging, while the hours put theirs in a line of prose underneath. Same badge, same place, same words.
- **A new shop's till starts at 3,000 gp**, up from 250 (`scripts/const.js`). The till is also the buyback ceiling — a shop cannot take what it cannot pay for — so 250 did not read as a modest shopkeeper, it read as a shop that refuses every sale the party actually wants to make. Unchanged in every other respect: it is seeded once, on enabling, and only when the Actor has no coin at all, so it never tops up a shop a GM has deliberately emptied.
- **Text over an illustration matches Minstrel’s weight** (`styles/window-shop.css`). Every line in their scene header runs at .9–.95 of one warm white; ours dimmed the secondary lines to .82, which is a light-card habit carried onto a dark ground — against parchment grey reads as quieter, against a photograph it just reads as harder. Hierarchy is size and weight now, not faded colour. Emphasis inside those rows had to be named rather than inherited: `.merchant-shop-reputation > strong` carries its own colour, so the band name and the pricing effect — the two words in that sentence anybody actually reads — stayed dark on a dark card.
- **A shop with an illustration reads like Minstrel’s sound-scene header** (`styles/window-shop.css`). Theirs is a background image under a gradient of `rgba(0,0,0,.01)` to `.15` — almost nothing — which works because their window and their art are both dark. Merchant’s window is parchment, so the ground has to come from somewhere, and three attempts got the trade wrong: a translucent card that washed the picture out, a left-to-right fade that hid half of it, then a veil so heavy the market became a dark rectangle. **Minstrel’s panel also carries a `min-height`, and that part does not transfer** — this card sizes to its content inside a column with no spare room, so a floor on it pushed the rows below straight out of the card. The picture gets whatever height the content comes to; the veil stays light, and a thin dark halo on the text handles the bright patches a lighter veil leaves in.
- **The compendium section is headed "Configured Compendiums"**, matching the Source it belongs to. It read "What this shop deals in", so the picker and the settings it governs had two different names and looked like two different features. Roll Tables already matched its own heading.
- **A newly dropped roll table draws ten, not one** (`scripts/const.js`). One roll is one row, and on a shelf carrying fifty products that is a delivery nobody notices arriving — the table had to be configured before it did anything worth seeing. Ten shows up on the first restock without being the whole shelf.
- **On a shelf drawing from both, Roll Tables now sit above Configured Compendiums on the card** (`templates/window-merchant-config.hbs`), matching the source's name and the order the draw actually runs in. A card listing them the other way round describes a different rule from the one running.
- **A shelf carries fifty products by default, not twenty-five** (`scripts/const.js`). A party after rope, a lantern, chalk and a crowbar can exhaust twenty-five in one visit; fifty is enough that the shop still has something the third time somebody walks in. The surrounding note is corrected with it: `maxProducts` stopped being a ceiling against runaway growth when a draw started bringing in new products only, and is now a target a drawing shelf fills up to. `maxPerItem` is still a ceiling and still guards its own runaway.

Manual is the only default that does nothing until asked. **Schema 5 stamps an explicit source on every existing shelf first** — tables if it has any, manual if not — so nothing stops drawing because a default moved. The legacy branch states its own source rather than leaving it to the second pass, which reads the *new* flag and so cannot see a shelf still on the old one: those are the oldest shelves in any world and the ones that would most surprise somebody by going quiet.

It is the one control in this window that creates something, and it sat as a bare `+` between a heading and a count, where it read as decoration on the count. A tooltip only helps somebody who already suspected the thing did something.

- **Chip-group labels sit above their pills** (`styles/window-merchant-config.css`), matching every other card-style setting here. A label beside a wrapping row aligns against whichever line happens to be last, which is why it read as floating.
- **The price range shows its value as a badge**, the way the Global Markup slider already does (`templates/window-merchant-config.hbs`). It was a line of prose under the track, which is a second spelling of a question the window already answers one way.
- **The filter pills are the control, not a label beside a checkbox** (`templates/window-merchant-config.hbs`, `styles/window-merchant-config.css`). A tick and a pill said the same thing twice. The input stays for keyboard reach and form semantics but is taken out of the picture visually — `appearance: none` rather than `display: none`, which would take it out of the tab order too. Selected is stated with fill **and** weight rather than colour alone, so it survives a monochrome theme.
- **The stocking-rules summary is stated once, above the shelves** (`templates/window-merchant-config.hbs`). It describes the *world*, so a copy on every inventory card repeated the same four lines five times and made each shelf look like it owned settings it does not.
- **The query's price window is a two-ended slider** (`scripts/const.js`, `scripts/window-merchant-config.js`), the same control the trading hours use. Stops are roughly logarithmic — shop prices span four orders of magnitude, so a linear range spends nine tenths of its travel in a band no shop cares about and cannot separate a torch from a lantern. The top stop reads **Any**, stored as `null`: `JSON.stringify(Infinity)` is `null`, so storing Infinity would come back meaning something different by accident.
- **Kinds and rarities are two labelled groups**, not two adjacent rows of identical chips — which read as one list of unrelated things and invited ticking a rarity to mean a kind.
- **The query source is called "Configured Compendiums"**, naming the GM's own configured search set rather than implying every pack installed.
- **Cross-client traffic goes through `blacksmith.sockets`** (`scripts/utility-sockets.js`, `scripts/manager-merchant.js`, `scripts/window-shop.js`). Slates, presence and refreshes rode a raw `game.socket` channel — the last place Merchant talked to core directly on a surface Blacksmith owns. Semantics are unchanged: their `emit()` with no options maps to `executeForOthers`, so it does not echo to the sender, which is what every handler assumes. One channel demultiplexed on an `action` field became four registered event names, each **module-prefixed** — Blacksmith keys external handlers in a flat Map shared by every consumer, so an unprefixed `slate` would silently overwrite another module's. A Blacksmith too old to publish `sockets` falls back to the exact wire shape the raw channel used.
- **`tests/test-sockets.mjs`** pins both paths: prefixed names and payloads through the hub, and the fallback binding a single listener however many events register — `game.socket.on` stacks rather than replaces, so binding per event would mean four handler calls per message.

## [13.0.1] - 2026-08-23

### Added
- **Localisation** (`lang/en.json`, every script and template). 309 keys; `lang/en.json` was a stub. Hook descriptions and console output stay English deliberately — they are read while debugging, not while playing. `const.js` is localised **at the point of display** rather than at definition, because it is evaluated before `game.i18n` exists; its literals are both the source text and the fallback, so an untranslated world reads English rather than a key. Sentences are one key with parameters rather than a concatenation: the reputation line was three fragments around two `<strong>` interpolations, which gave a translator three clauses they could not reorder.
- **`tests/test-i18n.mjs`**: every key asked for exists, every key defined is asked for, one namespace, no empty values, and anything containing `{placeholder}` is reached through `format` rather than `localize`. A missing key is not a crash — it renders as the key itself, which looks like text and only reads wrong, so it is exactly the class of mistake that ships.
- **A shop can give things away** (`scripts/const.js`, `scripts/utility-pricing.js`, `scripts/manager-merchant.js`, `scripts/window-shop.js`). Type **0** into a shelf price and the row reads **Free**; clear the box and it goes back to **no price**. Those are different states and could not previously be told apart: dnd5e leaves `system.price.value` at 0 on everything nobody has valued, so a bare 0 means "unvalued" far more often than it means "free", and treating it as free would have put every shop's unpriced stock on the house. `FREE_FLAG` carries the intent. Zero then survives the whole arithmetic — no markup, market rate or standing can put a price back on a giveaway — and a shop buys one back for nothing rather than for the one-base-unit floor. The flag is transient and omitted on exchange, like `par`: a cloak given away is still a cloak, and must not arrive in the buyer's pack claiming to be free.
- **A GM can set an item's price from the shelf** (`scripts/manager-merchant.js`, `scripts/window-shop.js`, `templates/partial-shop-row.hbs`): double-click the price on a stock row, the same gesture as the quantity beside it. It writes the item's own `system.price` rather than an agreement — what the thing costs, not what these two settled on for this trade. **A row reading "no price" was previously a dead end**: without a price the row cannot go on the slate, so the slate's price control could never be reached, and an item that arrived unpriced could only be fixed by leaving the shop and opening the Actor. The editor sits on the price *cell* rather than the figure for exactly that reason — an unpriced row has no figure to double-click. Not offered on an unpriced inventory, where having no list price is the point.
- **`listPriceBase(item)`** (`scripts/utility-pricing.js`): the item's own worth, before market, markup or standing. It is now the only reading of `system.price` in the module — `resolvePrice` multiplies it and the price editor writes it back, so the editor cannot open showing a figure the shelf would price differently.

### Changed
- **`changeRecipient` calls `blacksmith.dialog.pickActor`** (`scripts/window-shop.js`). Merchant and Curator had written the same thirty-five lines — an entity list inside a dialog, read back on confirm — and it is the hub's now, so the search field, avatars and keyboard behaviour are the ones every other Blacksmith list has. The private `_pickActor` and `documentation/plans/plan-extraction.md` are both deleted; every candidate that exercise raised has landed or been withdrawn. **Two behaviours went missing** and are asked for upstream: the picker opens on the first actor rather than the current one, and it no longer badges anyone with lines already on a slate. `entityList` supports badges; `pickActor` does not forward them yet.
- **A purchased inventory pays 70% by default, not 95%** (`scripts/const.js`). At 95% against a 5% resale markup the shop could be farmed: buy from the general shelf at `worth x reputation`, sell straight back at `worth x buyRate / reputation`, and the loop opens whenever `buyRate > markup x reputation^2` — which at a 5% markup is any rate above 72%. `MAX_BUYBACK_RATIO` caught it, but that meant the clamp governed rather than the slider, and because the cap falls as standing improves while the offer rises, **a party the town loved was paid less than a neutral one**: 84.8% at Legendary against 95% at Neutral. At 70% the slider is the number in force and standing helps monotonically — 54% hated, 70% neutral, 82% legendary. Regional arbitrage is untouched: that is the market rate, which deliberately does not invert.
- **Recorded Blacksmith's two contract changes of 2026-08-22** (`scripts/manager-merchant.js`, `documentation/architecture/architecture-merchant.md`). `BlacksmithHookManager` cancellation is now opt-in via a top-level `canCancel`; **nothing here changes**, because none of Merchant's nine hooks is a `pre*` hook and none cancels anything. The `createItem` watcher was returning whatever its helper returned, which is harmless on a post hook and is exactly the shape that used to veto item creation world-wide on a `pre*` one — it now explicitly returns nothing, so a future rename cannot turn it into a veto. The base-class import from `api/blacksmith-api.js` is documented as the supported contract rather than as a deliberate violation with a TODO against it.
- **`api.inventory` merges reliably now**, fixed upstream. Merchant saw the fault as duplicate rows on every restock. Nothing here was written to work around it — a roll adding new products only is a rule about what a restock *means* — but the drop path does merge, and the restock target it computes for a merged row is now load-bearing.
- **A roll brings new products, never more of what is already carried** (`scripts/manager-merchant.js`). Topping up is the refill's job and it refills to the level the GM set; a table adding to the same row pushed it past that level and made the number they typed mean nothing. `maxProducts` is now a **target** rather than a clip: a shelf that carries twenty and holds fifteen rolls for five more, and stops there.
- **How deep a row arrives is three ceilings, smallest wins** (`scripts/const.js`, `scripts/utility-pricing.js`, `scripts/settings.js`): **type**, **rarity**, then price. Type is first because it is closest to how a shop is pictured — ten torches, one breastplate. Rarity is the lever price cannot pull: two blades at one price are not the same question if only one of them is the only one anybody has heard of. Zero means a lever has no opinion, which is what `common` wants. They do not interact — each is a ceiling, so there is no order to remember. A quantity the **author** stated still wins over all three: the bands exist to invent a number when nobody stated one.
- **A delivery is never a single item unless the ceiling says so** (`scripts/utility-pricing.js`). The depth roll was uniform from 1, so 1 was exactly as likely as the cap and a shelf of twenty-five products landed about five of them single — one dagger, one dart. The roll now starts at half the ceiling, so the cap means *what this shop keeps* rather than *the luckiest thing that could happen*: a ceiling of 5 delivers 3–5, a ceiling of 10 delivers 5–10. A ceiling of 1 is still exactly 1, which is what keeps a legendary blade alone on the shelf.
- **The depth tables are world settings**, with one dial per inventory. How much rope exists and how freely plate moves are the same answers in every shop on the map, so they are set once in Merchant's module settings; each inventory gets **Sparse / Normal / Deep** scaling them. The card shows the summary and says where it is set — twelve controls per inventory would restate the same world in every shop in it.
- **A drop runs the same chain as a roll** (`scripts/manager-merchant.js`). A compendium entry reads 1 because that is what one crowbar *is*, not because a shop keeps one; taking it literally is what made every dragged row land as a single item. Armour still lands alone — that is rarity and price agreeing, which is the answer we wanted.
- **Stocking is its own section on the inventory card** (`templates/window-merchant-config.hbs`), above Restock. "How many" and "when" were one group and read as one decision, which is why the ceilings kept being mistaken for restock settings. Products and Max stack live there now, with the depth dial and the world summary.
- **`gm-request.js` is deleted, and the caller is verified** (`scripts/manager-merchant.js`, `scripts/window-shop.js`). Merchant carried its own GM request envelope from the first commit, always described as a bridge rather than a design, and it is now `blacksmith.gmRequest`. One op — `coffee-pub-merchant.settle` — registered on **every** client, because any of them can become the answering GM and one that registered nothing answers `UNKNOWN_OP`. A GM calling it runs the handler locally with no round trip, which is what makes a shop work in a world with nobody else connected.

  **The seam it closes is the one this module could not close from inside.** Foundry knows who sent a query and does not pass it to query handlers, so Merchant had been asserting the caller's id *in its own payload* — the step that turns a verified identity into a client-supplied claim. Building a mitigation for it was refused at the time, on the grounds that only the envelope could fix it. `_process(payload, user)` is now handed a `User` resolved from the authenticated socket, and the ownership checks behind `canActAs` and `_validateShopper` are worth what they say. The standing rule: **never read an identity out of a payload.** Three new refusals are explained rather than swallowed — `UNKNOWN_OP`, `QUERY_UNAVAILABLE`, and `IDENTITY_UNVERIFIED`, which is a refusal to report rather than work around.
- **Adopted `blacksmith.party`** (`scripts/manager-merchant.js`): `getPartyActor` and `getPartyCharacters` are now `party.actor()` and `party.acting()`. Their split is the thing this had no way of knowing it was missing — `resting()` is the party's *creatures* and includes familiars and companions, `acting()` is its player characters. A familiar rests with the group and cannot buy a sword, and picking the wrong roster gives one that looks right in testing and is wrong at a table with a druid in it. `hasPrimaryParty()` is available for the "no primary party set" case, which explains an odd Buying-as list better than the list does.
- **Hooks are registered under a context and can be disposed** (`scripts/manager-merchant.js`): the five `Hooks.on` registrations go through `BlacksmithHookManager` with a context, so `teardown()` can undo all of it. It used to dispose the token interaction claim and leave five callbacks running for the rest of the session. **No throttling on the hooks**, deliberately: a throttle drops whole events rather than coalescing them, so a burst touching two merchants could lose the second one's refresh entirely.
- **Refreshes coalesce per merchant** (`scripts/manager-merchant.js`): one gesture is rarely one write — dragging a stack fires `updateItem` per document, a table roll grants several rows, the migration touches every container a shop has — and each used to be its own socket emit and its own re-render on every connected client. They now merge per Actor over 60ms, which is where coalescing is safe because the key is what is being merged.
- **The migration runs before the watchers start listening** (`scripts/merchant.js`). It was the other way round, so every write the migration made announced itself to every client — a hundred socket emits at load in a world with twenty merchants, all reporting a change nobody could see yet.
- **`buyback` is gone from the vocabulary** (`scripts/utility-pricing.js`, `scripts/manager-merchant.js`, `scripts/window-shop.js`). `resolveBuybackPrice` → `resolvePurchasePrice`, `negotiatedBuyback` → `negotiatedPurchase`, `_buyback` → `_purchasedInventory`, and the stored `pricing.buybackOverrides` → `purchaseOverrides` under **schema 3**, which is the expensive half of a rename and the reason this waited. The old key is still *read*, for the window between a world loading and its GM logging in to run the migration: a player who opens a shop first should not watch an agreed price vanish and come back.
- **Thirty-four orphaned CSS rules removed**, left by features that were replaced — the old Buy/Sell/Checkout controls, the pre-redesign settings layout. Verified dead against every template and script, and two near-misses were checked and **kept**: `merchant-shop-cart-net-pay` and `-receive` are built as `merchant-shop-cart-net-{{netDirection}}`, so a grep for the literal class finds nothing while they are very much alive.
- **`api.worldClock` evaluated and declined.** Their scheduler answers "tell me when the world reaches a moment"; Merchant's two clock needs are "has enough time passed since a stored timestamp" (restocking) and "did a derived answer change" (trading hours). Neither is a moment. The reasoning is in `TODO.md` under *Considered, not scheduled*, so nobody has to re-derive it.
- **Regional pricing: a scene has a market** (`scripts/utility-market.js`, `scripts/merchant.js`). A **Local Market** entry on the Scene sheet's header sets what goods are worth there — ×0.25 to ×4.00, default the going rate — and every merchant on that map prices against it. It is the lever trade actually runs on: buy a 100gp trade good at ×0.50 for 50, carry it to a ×3.00 city and a merchant dealing dear pays 270 for it.

  **It multiplies both sides in the same direction, and that is the whole design.** Reputation is a *favour*, so it inverts — being liked means buying cheaper **and** selling dearer, both in the party's favour — which makes the best place to buy also the best place to sell, so no two areas differing only in reputation can ever be arbitraged. A market rate is not a favour; it is what the thing is worth. Where goods are dear you pay more **and** are paid more, and that asymmetry — bad to buy in, good to sell in — is what a trade route is. There are now three levers with three scopes: the market is the place, reputation is the place's opinion of the party, and Global Markup is one merchant against their competitors.

  Stored as a Scene flag, so it travels with the scene on export; setting it back to ×1.00 unsets the flag rather than storing a no-op. The shop window says *"Prices here run high"* only where it is true — a bill twice what a player expected is the town rather than the shopkeeper, and they should be able to tell which. A city across three maps means setting it three times; named regions are a bigger feature and wait until that actually annoys somebody.

  The loop stays shut: at one counter every place-and-shop multiplier appears on both sides and cancels, and the tests sweep markets, reputations, markups and purchase rates to prove the shop always charges more than it pays.
- **A merchant's markup now applies to what they pay, not only to what they charge** (`scripts/utility-pricing.js`). It was blanked on the sell side, on the reasoning that a dear quarter should not pay more for second-hand goods — wrong twice over. Global Markup is *one merchant's* pricing against their competitors, not the district's, so a shop dealing in dearer goods should pay dearer for them; and blanking it made trade impossible, because nothing about **where** you sold could change what you were paid. Buy from a merchant pricing at the going rate and sell to one at ×2.00 and the margin is the difference between their markups, less the second one's spread — which is what a trade route is.

  **Reputation cannot create a trade route, and that is correct.** It is the area's disposition toward the party, so it improves buying and selling together: the best place to buy is also the best place to sell, and no two areas differing only in reputation can turn a profit. Merchants create routes; reputation makes a good one better.
- **Fixed: a beloved party could mint gold at a generous merchant.** Selling an item and buying it back cancels the merchant's markup and leaves `buyRate / rep²` — reputation counted twice, because it makes buying cheaper *and* selling dearer. At a purchase rate of 0.9 in a legendary-reputation town that exceeds 1, so the round trip profited and repeated forever. Capping the purchase rate could not close it: the safe ceiling moves with reputation, so any fixed limit is too tight for a neutral town or too loose for a beloved one. **A shop now never pays more than 95% of what it would charge for the same item** (`MAX_BUYBACK_RATIO`), which is the same rule stated where it cannot be tuned out — and true of every dealer that has ever existed, so it needs no explaining. `tests/test-pricing.mjs` sweeps 300 combinations of shop markup, inventory markup, reputation and purchase rate and asserts the shop always charges more than it pays. **The bug was found by writing that test, not by playing.**
- **The stylesheet is split, one file per window** (`styles/`): `default.css` is now imports and nothing else, pulling in `window-shop.css`, `window-merchant-config.css` and `dialog.css`. It had grown to a thousand lines with shop rules and settings rules interleaved in the order they happened to be written, so finding the rule for a control meant searching the file rather than opening the one it belongs to. Curator and Squire are both built this way. All 352 rules were carried across unchanged and verified as an exact set before and after — `@container` blocks carrying rules for both windows were re-emitted into each file with their condition intact.
- **Settings reads as a form, not as prose** (`templates/window-merchant-config.hbs`, `styles/window-merchant-config.css`): every setting is a label with its control beneath it and its explanation beneath that. Controls embedded in sentences are gone — *"every [4] days"* is now **Frequency: Weekly**, and *"[25] products [3] each"* is now **Max stack**. Each inventory is a card with its own headings (Pricing, Restock, Roll Tables) rather than a row that grew settings, **Is a merchant** moved into the subject card where the biggest fact belongs, and the till shows a box per denomination pre-filled with what the shop holds. Rates are sliders showing all three numbers — both bounds and the current value — and say what they mean in the words already on the section: **markup** and **discount**, never *dearer*. Roll tables spell out what they will do: *"Draws 3 items from this table every time this inventory restocks."*
- **Fixed: the inventory cards rendered scrambled.** The markup was rebuilt but the old row's CSS was left behind, so rules like `grid-area: img` still applied to elements now inside a different grid — one with no named areas. A `grid-area` naming an area that does not exist is not ignored: it creates an implicit line and places the item there, which is why the artwork floated right, the buttons wrapped to their own row, and the name box was squeezed to "Storefro". Twenty-five stale rules deleted.
- **The till total says what it is.** The badge in the Till header reads *"Worth 23,854 gp 1 sp 8 cp"* — everything converted into the coins prices are quoted in, so a shop holding platinum shows a larger figure than its gold box. Unlabelled it read as a contradiction of the boxes beneath it.
- **Restock Everything is no longer the primary action** on a settings window, and the primary is **I'm Done**, which closes. Settings save as they are made, so there is nothing to commit — a **Saved** pip appears for a moment after each successful write, which is the acknowledgement that live saving otherwise lacks. It fires because a write landed, so it cannot claim a save that did not happen.
- **Files carry a role prefix, not the module's own name** (`scripts/`). `merchant-pricing.js`, `merchant-inventory.js`, `merchant-feedback.js`, `merchant-progress.js` and `merchant-reputation.js` are now `utility-*`. The prefix said nothing — this is the merchant module, so every file in it is a merchant file — and the suite's convention is `<role>-<subject>`: Blacksmith has 40 `manager-`, 24 `api-`, 21 `utility-`, 20 `window-`. Curator looks like a counter-example with its `loot-*` files, but there `loot` names a *feature within* the module; here it named the module. `manager-*` was the obvious alternative and is wrong twice over: only one of these is a manager, and two of the names it would produce — `manager-reputation.js` and `api-inventory.js` — are **files Blacksmith already has**, which is the exact tell `CONTRIBUTING.md` gives for a forked component. `window-merchant-config.js` keeps its name: other configs are plausible, so the subject is worth spelling out.
- **An inventory's artwork is bigger, and clicking it changes it** (`scripts/window-merchant-config.js`, `templates/window-merchant-config.hbs`): 56px, with a pencil on hover, opening Foundry's file picker at the current image. It writes the container's own `img`, so it changes here, in the shop window, and on dnd5e's sheet at once.
- **Rates are sliders** (`templates/window-merchant-config.hbs`): markup, and the purchased type's two rates, are ranges with a readout that repaints mid-drag and says what the number means — *"×1.35 · 35% dearer"*, *"pays 50% of worth"*. Same reasoning as the trading-hours slider: a rate is a position on a range, and dragging it says *dearer* in a way that typing 1.35 does not. The write happens on release, so a drag is one document update rather than one per pixel.
- **A purchased inventory has no roll tables and no restock** (`scripts/manager-merchant.js`, `templates/window-merchant-config.hbs`): no table row, no drop target, no restock button — and `restockInventory` refuses one outright, so **Restock Everything** and the world clock skip it too. Its stock is whatever the party sold it; there is no level to return to, and a table would be inventing goods the party never traded in.
- **The *products* ceiling is gone from the interface** (`scripts/window-merchant-config.js`): it was only ever enforced when a roll table fired, and the table's own roll count is how a GM says how much arrives — so on any inventory without a table it was a control that could not do anything, and on one with a table it was a second number for an idea already expressed. It survives as a constant backstop against an unattended reroll filling a shop. The other ceiling is now labelled **max N of each item** rather than *each*, and stays: it clamps a table roll *and* a quantity typed into the shop window, which no roll count knows about.
- **Shelves are now inventories, and an inventory has a type** (`scripts/const.js`, `scripts/manager-merchant.js`, `scripts/window-merchant-config.js`, `templates/window-merchant-config.hbs`). Six types — **General**, **Hidden**, **Premium**, **Discounted**, **Unpriced**, **Purchased** — replacing five presets named after furniture. The difference is not the words: the type is now **stored**, where before it was thrown away at creation. A Premium and a Storefront were the same object once made, so nothing downstream could offer a control that only made sense for one of them; that is why the settings window can now show a Purchase Rate on the one type that has one, and no price control at all on the type whose whole point is not having prices. A shop may hold several inventories of one type, and each has its own name — editable in Merchant Settings as well as on the container's own sheet. **The rename goes all the way down**: the stored flag, the CSS classes, the `data-*` attributes and the action names all say *inventory*, because one word in the interface and another in the code is how the two drift apart.
- **The type sets defaults; it does not take controls away.** Every inventory keeps the show/hide toggle in its header, including Premium and Discounted. That gesture exists so a GM can bring the good stuff out front mid-session, and losing it to gain a type would have been a bad trade. **Hidden** is simply the type that starts hidden and is allowed its own markup.
- **Markups stack, and the shop-wide one is now called Global Markup** (`scripts/utility-pricing.js`). It is a **baseline** — this shop is in an expensive quarter, or in the middle of nowhere — and an inventory's own markup is an adjustment *within* that shop, multiplied against it: a Premium at 1.5 inside a shop at 1.2 asks 1.8 times the going rate. It used to *replace* the shop's figure, which priced a premium inventory in an expensive shop as though the shop were ordinary. Any rate that is zero, negative or unparseable is read as 1, because a price of nothing is never what a typo meant.
- **Purchased inventories have two rates, not one.** **Purchase Rate** is what the shop pays for the party's goods; **Sell Rate** is what it then charges for them. One number could not be both, and the code carried a guard saying so — `resolvePrice` had to refuse to read a buyback shelf's markup, or a shop buying at half price would have resold at half price forever. With two fields the guard is gone and the GM sets each directly.
- **Reputation can move prices** (`scripts/utility-reputation.js`, new). Off unless a shop opts in. Blacksmith scores the party −100..+100 **per scene** and sorts it into eleven named bands; `REPUTATION_MARKUP` in `const.js` maps band to multiplier and is meant to be tuned. It applies on top of both markups when buying and **inverted** when selling — the standing that buys you a discount gets you more for your goods, or a beloved party would be rewarded in one direction and ignored in the other. An agreed price is never re-cut by it. Two constraints shaped the implementation: the band lookup is async, so it is resolved **once per render** rather than per row; and reputation is per scene, so a shop reads the scene its **token** stands on, never the GM's current view — otherwise a GM answering from another map would price the shop differently from the players standing in it.

  Blacksmith's scale briefly carried an `effects.merchantModifier` slot and they removed it rather than fill it. That was the right call and the boundary is worth stating: they own how liked the party is, we own what a shop does about it. The same scale drives NPC attitude and what people will tell you, and a table wanting gentler prices should not have to edit that.
- **The shop-wide Stock setting is gone**, and restock is part of every inventory (`scripts/manager-merchant.js`, `scripts/window-merchant-config.js`). This reverses an earlier decision, and the inheritance it removes was not wrong so much as invisible: two places set one thing, one of them silently, and a GM reading "Same as the shop" could not tell what it meant without going to look. **Purchased** is the one type with no restock choice, and says so instead — its stock is whatever the party sold it, so a refill would conjure duplicates of somebody's old sword.
- **The two ceilings are only shown where they can fire.** `maxProducts` is enforced in exactly one place — trimming a table roll — so on an inventory with no roll table it was a control that did nothing at all, and it now appears only when there is a table. `maxPerItem` clamps a table roll *and* a quantity a GM types in the shop window, so it appears wherever stock is counted. Neither was redundant with the roll count, which caps one delivery rather than what accumulates over months; they were simply on screen in places they could never act.
- **Existing shops are migrated, once** (`scripts/manager-merchant.js`, `scripts/merchant.js`). `migrateWorld()` runs GM-only from `ready`, rewrites each container's flag to the new key, derives its type from what the old settings must have meant, drops `mode`, and deletes the old flag in the same update so no container ever carries two answers. Stamped per merchant with a schema version, so a second GM logging in does not repeat it and a shop with no inventories is not re-examined for the rest of its life. The derivation also runs on read, for a world whose GM has not logged in yet or a container copied in from elsewhere.
- **The window base comes from the documented bridge** (`scripts/window-shop.js`, `scripts/window-merchant-config.js`): `import { BlacksmithToolWindowBaseV2 } from '/modules/coffee-pub-blacksmith/api/blacksmith-api.js'`. Blacksmith added the re-exports after Merchant broke a live world following the old advice to resolve the class from `module.api` at module scope — module scripts are evaluated before `game` exists, and ESM caches the failed evaluation, so the throw killed the module for the session rather than being retried.
- **Fixed: a window that failed to render could not be reopened for the rest of the session** (`scripts/window-shop.js`, `scripts/window-merchant-config.js`). Both windows kept their own one-per-target registry, and entered it *before* the first render but left it only in `_onClose`. So a render that threw — a shelf flag, a roll table uuid that no longer resolved, a template field that was not there — left an instance registered that had never opened and would never close, and every later open took the "already open, focus it" branch and re-rendered that same broken instance. The shop or the settings window was then unopenable for that actor until the page was reloaded, which is why it looked unreproducible: the registry is a static map and a reload clears it, while position and titlebar state live in `localStorage` and do not. Both registries are now `BlacksmithToolWindowBaseV2.openFor`, which deletes the entry when a render throws, deregisters identity-checked on close, and keys per subclass so a Shop and a Loot window on one token do not evict each other. Anything the shop does in `_onClose` now runs inside a `try`, because a throw before `super._onClose` would strand the entry the same way — presence-clearing is a socket emit, and a face left behind is a cosmetic bug where a stranded entry is not.

### Fixed
- **Four things read `game` while the module was still being evaluated** (`scripts/window-merchant-config.js`, `scripts/settings.js`, `scripts/window-shop.js`). `METHOD_LABELS` was a top-level object of already-translated strings, `SOUND_SETTINGS` a module-scope array, and `ShopWindow.SELL_SORTS` a **static class field** — all three evaluated at load, where `game` does not exist yet, and ESM caches a failed evaluation so the throw kills the module for the whole session rather than retrying. Tables now hold keys and the text is resolved when it is shown. Two further replacements had landed **inside HTML template literals without `${}`**, so the Restock Everything and Clear Slate tooltips would have rendered the literal source text — visible only on hover, which is why a passing test run missed it.
- **`tests/test-i18n.mjs` now fails on any `game.*` read outside a function body**, which is what makes the above a rule rather than a lesson. It walks a real scope stack with strings, templates and comments blanked first, because an indentation heuristic catches neither of the shapes that actually bit: a top-level object literal and a `static` field both look like ordinary indented code.
- **The restock clock ticked on the template and not on the shops** (`scripts/manager-merchant.js`). `_applyRestocks`, the trading-hours redraw and `migrateWorld` all walked `game.actors`, which contains the sidebar entry an unlinked merchant is cast from but none of the tokens actually standing on a map. So a merchant placed as an unlinked token never restocked, while the mould it came from restocked on schedule — and because an unlinked token inherits anything its delta has not overridden, the template's new stock was then *delivered* into every copy. Not a shop restocking; a leak with a schedule. `worldMerchants()` now yields linked merchant Actors (a linked token *is* its Actor, placed or not) and every unlinked merchant token across every scene, and yields a sidebar template not at all. `migrateWorld` still walks the wider set, because a template holds the flags every future placement inherits.
- **"Restocks the same items" could never put anything back** (`scripts/manager-merchant.js`). Par — the level a row is restocked to — was written only when a GM typed a quantity by hand. Everything that arrived by roll table or by drag had none, and `getStock` fell back to *the quantity currently on the shelf*, so the target followed the stock downward: selling three of four flutes silently set the target to one, and selling the last set it to zero. The refill loop then compared `available >= par` and skipped every row it was meant to fill. **The failure was invisible** — the shop looked stocked, the restock reported success, and nothing moved. Par is now written on every change that is not a sale, and schema 4 stamps one onto every existing row that lacks it.
- **Every restock added duplicate rows instead of stacking** (`scripts/manager-merchant.js`). Two Torch lines, two Flutes, one new set per restock. A roll now brings **new products only** and never touches a row the shelf already carries — see below — so the merge that was failing is no longer attempted.
- **Selling: the item card and the GM's click-to-open worked on the wrong Actor** (`scripts/window-shop.js`, `templates/partial-shop-row.hbs`). Both Actors put rows through the same partial and nothing in the markup told them apart, so both looked every row up on the merchant. In sell mode the rows are the shopper's pack: the lookup found nothing, so hovering a name or image showed no card and a GM clicking the image silently opened nothing. Rows now carry `data-owner`, the way slate lines already carried `data-line-side`.

It was per-client and per-token, so a GM had no way to see what a player had on their slate — which made the whole negotiate workflow unusable, because prices are agreed *on slate lines* and the GM could only ever see their own. Switching "Buying as" now switches slate, and switching to a player's character shows the slate that player is looking at, live, with every line and price editable.

  The slate carries the shopper's **portrait and name** in its title. Clicking a face on the bar swaps the whole panel underneath you, and a slate belongs to a character rather than to whoever is looking at it — so the panel says whose it now is rather than leaving you to remember.

  A face means **anyone shopping**, not anyone with something on the slate — someone who has the shop open and has taken nothing is still a person standing in the shop, and the row would be empty for most of a visit if browsing did not count. The mark on a face says whether that character has lines on the slate; the face itself says they are here.

  The faces on that bar come from a **presence** broadcast, not from the slates. Drawing them from slates read well and was wrong for the person it mattered most to: slates are mirrored only to clients that can act as that character, so a player saw an empty room however busy the shop was. Presence is about the *room*, so it goes to everyone; only what you can *do* with a face is gated. Everybody sees who is here, a face carries a mark when that character has something on the slate, and a face you could act as — in practice the GM's view of a player — is a button that takes the slate over. Anyone else's is a portrait, and does not invite a click it would not honour.

  Mirrored peer to peer rather than brokered by the GM, and **display only** — settling re-derives every line and every price on the GM regardless, so the worst a bad message can do is show somebody a wrong list. This is Curator's loot presence in a different coat, including the `ping` on open so a window arriving late sees the room rather than an empty one; the shapes are close enough that a shared mechanism is worth measuring once both have settled.

  Still not persisted. A slate is a half-formed intention, and a session-scoped mirror expires by itself rather than needing a rule about when somebody's abandoned cart goes stale. Permissions need no special handling either: the only characters you can switch to are the ones you can act as, so a player sees their own slates and a GM sees everyone's, for free.

  The character picker badges anyone with lines on the slate, because a GM has to know somebody is mid-purchase before it occurs to them to look — a shared slate nobody can find is not shared.
- **Fixed: picking things to sell did nothing.** `dialog.wait` hands a button callback **the dialog's form**, and runs it *after* the dialog has closed — not `(event, button, dialog)`, which is DialogV2's own shape that `wait` wraps rather than passes through. Reaching for `dialog.element` got `undefined`, so the selection read came back empty and the whole gesture silently did nothing. Both pickers in this module were affected. The signature is stated plainly in `api-dialog.md`; it was inferred from Blacksmith's internal wiring instead of read, which is the exact failure `CONTRIBUTING.md` §3 exists to prevent.
- **Money moves as one exact payment, and "cannot make change" is gone** (`scripts/utility-pricing.js`, `scripts/manager-merchant.js`): a settlement used to be a payment plus change handed back, which meant the *other* side had to be holding particular coins — and nothing guarantees a shop sitting on twenty thousand gold has six silver in the drawer. That refusal was the most common way an ordinary purchase failed, unfixable from the player's side and baffling from the GM's.

  The payer now re-cuts their own purse first when it has to be re-cut, so the exact coins exist to hand over and there is no change leg at all. Breaking a gold piece into ten silver is what a person does at a counter without thinking about it, and it is **value-neutral** — the same money in different coins — which is why it can sit outside the atomic part without reintroducing a half-completed trade: a failure at any point leaves the payer exactly as rich as they were. It goes through `setCurrency`, so it takes the inventory lock rather than racing the settlement it is preparing for.

  Platinum is left where its owner put it unless the working coin genuinely cannot cover the price, because it is a store of value somebody chose to hold rather than small change. Electrum is never handed to anybody who did not already have it. A refusal now means only what it should: not enough money. Covered by 249 exhaustive settlements asserting that every payment is exact, that re-cutting never changes a total, and that nothing is ever paid in coins the purse does not hold.
- **Fixed: toasts were nearly unreadable.** The palette was taken from the windows — the same green as the Open sign, the same red as Always closed — and `styles/toast.css` paints `rgba(20, 20, 20, 0.9)` behind a toast. Colours chosen to sit on parchment have nowhere near the contrast to sit on that, and one `color` drives border, icon and title together, so the whole toast suffered rather than just its trim. Same four hues, lifted for a dark surface and pitched to sit beside the body text the stylesheet already uses.
- **Fixed: "the till cannot cover it" was said of a till holding 20,000 gold, and sometimes to the wrong party.** The refusal fires in both directions — the merchant owing change, and the shopper owing it back when the merchant overpays — and said the same thing either way. It now names the side that is actually short and *which coins*, because a till with twenty thousand gold and no silver is not short of money, it is short of change, and those have different fixes.
- **The till is written under the inventory lock** (`scripts/manager-merchant.js`): `setTillGold` goes through `inventory.setCurrency` rather than a raw `actor.update()`. The raw write took no lock, so since `exchange` shipped a GM adjusting a till mid-session could have their edit silently discarded — the settlement reads the balance under the lock, the unlocked write lands, and the settlement writes `stale + delta` over the top. The boundary that decides this is not whether an operation has a counterparty but **whether the Actor takes part in locked operations**, and a shop does. Only `gp` is named, so the rest of the purse is left alone rather than zeroed.
- **`par` no longer rides out on sold goods** (`scripts/manager-merchant.js`): the settlement passes `omitFlags`, so a shelf's restock target is stripped from an item before it reaches a buyer. The same path goes in `ignoreFlags` too, and will stay there for a while: anything bought *before* this landed carries `par` on the buyer's row, so an arrival without it would compare as different and create a second stack rather than merging — a silent, self-inflicted duplicate-row bug with a long tail. The buyback guard in `getStock` stays regardless, because it covers items already sitting in worlds.
- **Everything the module says now goes through Blacksmith's toast API** (`scripts/utility-feedback.js`): 51 call sites converted from `ui.notifications`, which is a core-styled text queue — not themeable, no image slot, and nothing to be done with one except read it before it goes. A completed transaction is now a **receipt**: what was paid as the headline, who and where underneath, persistent until clicked, because money changing hands is the one moment somebody wants to check twice and an eight-second toast is one they read half of. A second purchase replaces the first rather than stacking. Two things deliberately stay on core notifications: the fallback for a Blacksmith too old to have the API — a world one version behind should lose the styling, not the message — and the restock progress bar, because a toast has no progress shape and core's does.
- **Six sound settings** (`scripts/settings.js`): adding to the slate, changing a quantity or price, taking a line off, completing a transaction, finishing a restock, and anything that errors. Choices come from Blacksmith's `arrSoundChoices`, so Merchant offers the same library as the rest of the suite and ships no audio of its own; the list rebinds on `blacksmithUpdated` for worlds that load it late. **World-scoped but played locally** — a shop's voice is set dressing and belongs to whoever built the scene, while broadcasting would mean the whole table hearing somebody else drop a rope into their own slate. All default to silent. `notify.error()` plays its sound itself rather than trusting twenty-odd call sites to remember, and the transaction sound rides on the receipt toast so the two cannot come apart.
- **Fixed: the character picker could return a character you did not pick.** `entityList.getSelectedIds()` shares `getSelection()`'s fallback — when `attach` did not find its input it hands back *the selection the caller passed in*. In the "Buying as" dialog the caller passes the current character, so a player switching to somebody else would have been handed back the one they were already on, silently and with no way to tell. The sell picker had the milder version: an empty initial selection meant picking six things and having nothing happen. Both now read the checked inputs out of the dialog, which is correct either way because only *binding* can fail. Interim: Blacksmith is shipping `entityList.readIdsFrom(root)`, which is this with the input name it already knows.
- **Fixed: a buyback shelf could manufacture stock it never had.** `registerTransientFlag` hides a flag from *merge comparison* but does not strip it from the payload, so `coffee-pub-merchant.par` travels out with every item bought from a counted shelf and travels back if the buyer sells it. A bedroll bought from a shelf kept at six arrived on the buyback shelf still claiming a par of six, and the next **Restock Everything** refilled that row to six — five bedrolls out of nothing, from a target the shop never set. A buyback shelf now ignores a stored par outright, which is correct on its own terms: its stock is whatever the party sold it, and there is nothing it is *kept at*. Blacksmith's forthcoming `omitFlags` will stop the flag arriving at all; this guard stays after it, because it covers every item already sitting in a world with the flag on it.
- **Reverted the INSUFFICIENT_QUANTITY workaround** (`scripts/manager-merchant.js`): Blacksmith took the fix within a day — `_resolveQuantity` now takes a `drawsDown` flag, false from the grant path and the `copy` leg, true from the three transfer paths — so a rolled row is one entry carrying its quantity again rather than N entries of one. What stays behind is the diagnosis: a refusal carrying `INSUFFICIENT_QUANTITY` can now only mean an out-of-date Blacksmith, and says so in the console and to the GM. Without that, the symptom is every row arriving at one or not at all, which looks exactly like a Merchant bug and cost a full debugging round the first time.
- **Fixed: rolled stock was refused as INSUFFICIENT_QUANTITY.** Asking `grantItems` for five crowbars from a compendium failed, because the grant paths run the same quantity validation a *transfer* runs — the source document's own `system.quantity` becomes a ceiling, and for a compendium template that is 1. A grant draws nothing down and has no source to be insufficient, so this is a defect rather than a rule; it is raised with Blacksmith. Until it lands, a depth of five is sent as five entries of one: duplicate entries in a batch are documented to coalesce into a single row holding the summed quantity, and both the merge and create paths do sum. Still one call, still two writes, and `itemUuid` is kept rather than switching to `itemData`, which would lose the compendium provenance. Stackability is also now read off the document — no `system.quantity`, no stack to deepen — which is the same rule the inventory API states for itself.
- **A negotiate shelf never shows a figure** (`scripts/window-shop.js`, `templates/partial-shop-row.hbs`): not even after a price has been agreed. The agreement is between the GM and whoever is standing at the counter; putting it in the price column publishes it to the next player who opens the shop, and turns a shelf that exists in order *not* to have prices into one that quietly accumulates them. The shelf is checked before any figure, so an agreed price can never leak into the column. In its place the GM — and only the GM — gets a tooltip carrying what they actually need: the agreed price if one has been named, otherwise what the thing is worth on the books as an anchor to haggle against. The context decides that, so a player inspecting the markup finds nothing to read either.
- **Item pictures are hot** (`scripts/window-shop.js`): the system's item card now hangs on the image as well as the name, on shelf rows and slate lines alike. The picture is the other half of what a person points at when they mean "that one", and reaching past a 32-pixel icon to a truncated name was a worse gesture than either. For a **GM**, clicking the picture opens the item — the way to fix a price, edit a description, or see what a rolled result actually is, without leaving the shop to find the shelf it is sitting in. GM-only and enforced by not binding it rather than by refusing inside the handler, so the cursor changes only where the click works: the affordance and the permission are the same fact.
- **Clear Shelf** (`scripts/manager-merchant.js`, both windows): takes everything off a shelf and leaves the shelf, with everything it is set to. It sits between the two controls that already existed and were both the wrong tool: setting a count to zero says *sold out*, deleting the container says *this shop has no such shelf*, and re-rolling a shop's stock needed neither. One `deleteEmbeddedDocuments` for the lot. Confirmed, unlike removing a single row — one item is easy to put back, nineteen and a table roll are not.
- **Restocking says what it is doing** (`scripts/utility-progress.js`): a shop with two shelves and four tables at ten rolls each is forty `table.roll()` calls and forty compendium lookups before a single item lands, and nothing on screen admitted to it. That is seconds of apparent nothing, which reads as nothing having happened, which is how a GM comes to press Restock Everything twice. Now a progress bar names the shelf and the table it is on. It is **core's** progress notification (`ui.notifications.info(msg, { progress: true })`), not one of ours — Blacksmith has no progress primitive and inventing one would be a second thing doing a job core already does. The bar is sized from the same arithmetic the work spends, so it ends exactly where the work does.
- **Fixed: rolled stock ignored the price bands entirely.** The depth rule had a whitelist of stackable *types* in front of it — consumables and loot stack, gear does not — which excluded daggers, vials, clothes, chests and tools, which is to say a general store's entire shelf. Every row still arrived at QTY 1 and the feature was invisible. Price was always what the intuition meant: a 1 gp vial lands deep, a 1500 gp suit of plate lands alone. Nobody has eight suits of plate because plate is expensive, not because it is armour. The type gate is gone rather than kept as a modifier.
- **Fixed: stocking failures were reported as a shrug.** `grantItems` returns results index-aligned with what was sent and entries fail independently, so the top-level flag alone said only "something went wrong somewhere" — the console read `{ ok: false, results: Array(20) }`, which names neither the row nor the reason. Failures are now listed individually with the item name and the reason, and the count a restock reports no longer includes rows that never arrived.
- **Fixed: deleting stock faster than the window re-renders.** The row is still on screen because the render that would have removed it has not landed, so a second click sent the same id and Foundry answered `Item "..." does not exist!` — a server round trip reported as an error for something the GM did correctly. The id is claimed before the first await and released in `finally`, the document is re-read after the await rather than trusted from before it, and losing the race to somebody else is no longer worth a red line.
- **Table-rolled stock arrives in believable amounts** (`scripts/utility-pricing.js`, `scripts/const.js`, `scripts/manager-merchant.js`): a roll used to deliver exactly one of whatever it drew, so twenty rolls produced twenty rows of QTY 1 and there was no setting anywhere that changed it — "each" was a ceiling that only ever refused, and par fell back to "as many as are there", which was one. Depth is now decided in three steps: **what the item says it is** (a compendium entry authored as a quiver of twenty arrives as twenty — we were throwing away the only statement anybody had actually made), then **what it costs** for anything a shop keeps a pile of (cheap things come in piles, dear things come singly; the band sets a ceiling and the depth is rolled inside it, so stocking the same shelf twice does not produce the same shop twice), then **one** for everything else, because nobody has eight suits of plate. Ammunition is the exception among weapons and stacks. The shelf's own "each" limit clamps the result, so a number a GM set by hand is never argued with by a die.
- **Negotiated prices** (`scripts/utility-pricing.js`, `scripts/manager-merchant.js`, `scripts/window-shop.js`): a GM double-clicks the price on any slate line and names it, for buying and for selling both. The Barter shelf is now **Negotiate** (label only — the stored mode is still `barter`, so existing shelves keep working) and its rows add to the slate like any other, at **TBD**, rather than showing an "Ask" label that named the thing to do and then left you to do it elsewhere. Settling refuses while any line is still TBD. The agreed figure is written to the **merchant document**, never carried in the settle request: a price is the one number in a transaction a player must not be able to name, and a slate is client state. An item that arrives with no price of its own is stamped with what was agreed, so a curio negotiated at 200gp can be sold on for 200gp; an item that already had a price keeps it, because a haggled discount is not what a thing is worth. Agreements are cleared once the trade they were made for settles.
- **A shop can be shut for good** (`scripts/const.js`, `scripts/window-merchant-config.js`): dragging the two trading-hours handles onto each other used to read as *always open*, which meant the slider had two gestures for open and none for closed. It now reads as **Always closed**, the mirror of the band drawn across the whole day, and both labels repaint mid-drag rather than on release. The label lost its border: it is a statement about the slider, not a button to press, and the box made it look like one.

The sheet actions exist because the shop claims left double-click on the token, which is how a GM would otherwise reach the Actor. In micro-titlebar mode the window base folds all three into the context menu.

The config window is for setting a shop up; this is for running one. Considered and rejected: using the container's `equipped` state for this. It is inert on containers so it would have worked, but it is transient state the ecosystem clears on transfer, it can change without anyone deciding to — a GM tidying inventory would silently hide a shelf — and it would split the shelf schema across a system field and a flag.

The schedule proposes and the toggle disposes — a GM can override at any time and the override stands until the next opening or closing hour. The override is derived rather than stored: it is the state disagreeing with the schedule, so the next crossing clears it by doing the ordinary thing. Overnight schedules work, hours come from `game.time.calendar` rather than assuming a 24-hour day, and the watcher compares the schedule before and after a jump so advancing eight hours at once still lands correctly.

A closed shop still opens for a player — they can look through the window — but no acquire controls appear and a crafted request is refused with `SHOP_CLOSED`. ### Changed
- **The Actor sheet header carries Merchant Settings only.** The Open Shop entry is gone — opening a shop is the token's job, and the sheet is for setting one up.
- **Prices** (`scripts/utility-pricing.js`): each row shows what it costs, resolved from a per-item override, then the shelf or merchant markup applied to the item's own `system.price`. Denominations, labels and conversions all come from `CONFIG.DND5E.currencies` rather than a hardcoded table, and everything is counted internally in the smallest denomination so the arithmetic stays in integers. Markup is editable in the config window.
- **Cart and checkout** (`scripts/window-shop.js`, `scripts/manager-merchant.js`): add items to a cart and pay for the lot at once. Checkout is a single `exchange` — one payment and one lot of change — rather than a purchase per line, which would be more writes and would round each line's change separately. Every line is re-priced on the GM at checkout rather than trusting what the cart was built against, and stock removed while a cart sat open drops out of it quietly.
- **Rows read as columns**: item, quantity available, price, actions. Price is its own column rather than a note in the subtitle. Quantity shows ∞ while stock is infinite, so finite stock later fills the same column without moving anything.
- **One Buy control instead of three destinations**: Buy asks who the goods are for — the acting character, another party member, or the party — rather than encoding three places in three icons a player has to learn apart. **The shopper always pays**, wherever the goods land: buying for the party or for another character is a gift, and a gift comes out of the giver’s purse.
- **Paid delivery to anyone but the shopper is refused for now** (`THIRD_PARTY_DELIVERY`). The shopper paying while someone else receives is a **three-party** transaction — merchant, payer, recipient — and `exchange` is two-sided, so it cannot express it. Refused explicitly rather than silently charging the wrong purse, and the destination dialog says so before the choice is made rather than after. Raised with Blacksmith while `exchange` is still being designed.
- **Buying and selling** (`scripts/manager-merchant.js`, `scripts/window-shop.js`): a Buy control priced per row, and a Sell control that offers whatever the buyback shelf would take. Payment is an `exchange` so coin and change commit together. **Delivery is separate**, because `exchange` *moves* what it is given and a shop's stock is a count: handing it the merchant's item would sell the template itself and empty the shelf on the first purchase. Goods go first, so a payment that fails leaves the player holding the item and the shop out of pocket rather than the reverse. An `exchange` side that could say *copy* would collapse this back into one atomic call, and that has been raised. **`blacksmith.inventory.exchange` does not exist yet**, so both controls are **disabled and say why on hover** rather than being absent. This reverses the earlier rule. An absent button reads as “this shop does not do that”; a disabled one naming its reason reads as “not right now, and here is what would change it” — and the row does not reflow on the day the primitive lands.
- **Stock policy** (`scripts/const.js`, `scripts/manager-merchant.js`, `scripts/window-shop.js`, `scripts/window-merchant-config.js`): a shelf either never runs out, runs out, or runs out and refills. The setting is **per shelf** and falls back to the shop's, the same inheritance `markup` already uses — so a Storefront that restocks nightly and a Back Room holding three unique things are one merchant. Buyback is always finite: restocking it would conjure duplicates of somebody's old sword.
- **Stock is a count, not a document.** Every policy grants the buyer a *copy* and adjusts `system.quantity` on the merchant's own item; nothing is ever moved off a shelf by a sale. That is what lets a sold-out row stay put marked out of stock, which finite stock prefers and restocking stock requires — a deleted row is not a row anything can restock. The count lives in `system.quantity` rather than a flag of ours so the Actor sheet, the shop window and every other module read the same number.
- **Quantities are editable in the shop window** (`scripts/window-shop.js`): a GM types a number straight into the quantity column on any shelf that counts its stock, and that sets **both** what is there and what a restocking shelf refills to. A purchase lowers the count and leaves the target alone. No second par editor to keep in sync.
- **Restocking runs on the world clock** (`scripts/manager-merchant.js`): a restocking shelf refills every *n* in-world days, riding the same `updateWorldTime` watcher that already opens and closes shops rather than registering a second one. Elapsed time against an interval rather than counted boundaries, so advancing a week restocks once — a shop is full again, it does not accumulate seven days of stock. A GM can also refill a shelf on the spot from Merchant Settings. Winding the clock backwards resets the shelf's timer rather than stranding it in the future.
- **The concurrency loot needed is back** (`scripts/manager-merchant.js`): infinite stock had no races at all, because the merchant was never mutated. Finite stock means two players can read the same count, so every read-then-write goes through a per-merchant promise chain. Sound because exactly one client runs it: `activeGM` is core's own deterministic designation, so there is no second process to coordinate with.
- **Making change** (`scripts/utility-pricing.js`): `api.inventory` never converts denominations, so Merchant works out which coins change hands. Payment spends smallest coins first and returns the overpayment as change — what a person does at a counter, rather than what an optimal coin-counter would do. Affordability is judged on the whole purse, checked in the window before the GM is asked and again on the GM before anything moves.
- **Logic checks** (`tests/`): two dependency-free Node scripts covering the parts that are pure arithmetic
  and pure control flow — making change across every combination of a small purse against seven prices, and
  the stock policy, restock cadence and lock behaviour. They cannot catch a wrong document path or a missing
  template field, which is most of what goes wrong in a Foundry module; they catch the half where reading the
  code is a bad way to find a bug and a wrong answer is silent.
- **Two workarounds deleted** (`scripts/window-shop.js`, `scripts/utility-inventory.js`): the frame-polling
  control attach is gone, because `blacksmith.dialog.wait()` now takes `controls` and binds them after every
  render; and the post-grant container correction is gone, because `grantItem` takes a `container` and always
  writes `system.container` rather than inheriting the source's. Container membership is part of merge
  identity, so a merge can only land on a row already on that shelf — which was the case the workaround was
  carefully skipping.
- **`exchange` is a list of directed transfers, not two sides** (`scripts/manager-merchant.js`): the shape is
  decided — `{ transfers: [{ from, to, items, currency, container }, ...] }` — and Merchant is written
  against it. A shop transaction is not reliably two-party, and a list of what each party *gives* does not
  say where any of it goes once there are three of them; two-sidedness was silently carrying the routing.
  Selling is one transfer of goods and two of coin, payment and change never netted, because netting would
  let a payer hand over coin they do not have.
- **Search** (`scripts/window-shop.js`, `templates/window-shop.hbs`): a box in the pinned header filters the
  stock by name or kind, so "potion" finds a Potion of Healing and "consumable" finds the category. A shelf
  or a category with nothing matching collapses entirely rather than leaving a heading over nothing, and each
  shelf's count shows what is in front of you until the search is cleared.

  **Filtered in the DOM rather than in the context, deliberately.** Filtering in `getData` would mean an
  async render per keystroke, which rebuilds the markup and takes the caret out of the box being typed in.
  Instead the query lives on the window and `_onRender` re-applies it — so typing never re-renders, and a
  refresh, a GM stocking a shelf, or another player's purchase never drops a standing search. The filter is
  an exported pure function of markup and query, which is what lets `tests/test-search.mjs` run it against
  the real compiled templates.
- **A shop has a kind and a description** (`scripts/const.js`, `scripts/window-merchant-config.js`): twelve
  kinds — General Store, Weaponsmith, Apothecary, and so on — replacing the word "Merchant" above the name,
  which was telling the player something they could already see. Flavour only; nothing is restricted by it,
  and a weaponsmith with a shelf of potions is a perfectly good shop. The description is optional free text
  shown under the name, run through Foundry's enricher so journal links and inline rolls work. It is
  GM-written by construction and a failed enrich yields nothing rather than the raw string, so there is no
  path where unescaped input reaches a player's window.
- **Adding a shelf is a menu, not a row of buttons** (`scripts/window-merchant-config.js`): a **+** on the
  Shelves header opens Blacksmith's context menu with the five presets. Adding a shelf happens about once per
  shop, and a permanent row of five buttons was paying for that in window height every time the window was
  open for anything else. Falls back to a picker dialog where the menu API is unavailable.
- **Shelf artwork is Foundry's container icons** rather than the monochrome `icons/svg` set: a crate, a
  reinforced chest, a steel chest, a woven basket and a cloth sack. A shelf is a physical thing in the shop
  and reads better as one, and these ship with core.
- **The trading-hours handles are coloured** (`styles/default.css`): the opening handle green, the closing
  handle red, and the readout labels to match. The band between them says the same thing, but four pixels of
  dark green over a sunken track is nearly invisible on the light themes — so the colour that has to read is
  on the thing you grab. The band is thicker and lighter for the same reason.
- **A shelf's name is the container's name** (`scripts/const.js`, `scripts/manager-merchant.js`): the shelf
  flag used to carry its own `label`, so renaming the container in dnd5e's sheet renamed it everywhere in
  Foundry and nowhere in Merchant — the shop went on calling it Barter. Nothing stops a GM renaming a
  container, so the fix is to follow the rename rather than to fight it. There is now one name and the flag
  carries no copy of it. Old flags keep a vestigial `label` that is ignored.

  too, which is a real question with a wrong answer that orphans everything inside.
- **A typed quantity is clamped to the shelf's ceiling, and says so** (`scripts/manager-merchant.js`,
  `scripts/window-shop.js`): typing 10 into a row on a shelf that holds 5 of anything used to store 10 while
  the restock target read 5 — two numbers disagreeing with nothing to explain why. It clamps now and tells
  you where the limit is raised. One number governs.
- **The trading-hours slider reads against the day** (`templates/window-merchant-config.hbs`): the day's ends
  flank the track, because a band means nothing without the span it sits in. The chosen hours read as one
  phrase above it rather than two labels facing each other, with the opening figure green and the closing one
  red to match their handles. Deeper channel, larger handles.
- **"Always open" is a label, not a button** (`scripts/const.js`, `templates/window-merchant-config.hbs`):
  it was a control that cleared the schedule, which meant two ways to say one thing and a way for the two to
  disagree — a shop could be scheduleless *and* have hours that covered the day, and those looked different
  while meaning the same. Covering the whole slider is what makes a shop always open, and the label says so.

  **The closing handle now reaches the end of the day rather than its last hour.** That is what makes it
  arithmetic rather than a special case: `0–24` is genuinely every hour, where `0–23` left 11pm outside. A
  shop with no schedule at all shows the handles across the whole day, because that is what it is doing.

  The shop window stops printing hours for a shop open all of them — "midnight to midnight" is a fact about
  the clock rather than about the shop.
- **Restock Everything** (`scripts/window-merchant-config.js`): the main action in Merchant Settings,
  right-justified like the shop's. Brings every shelf back to its quantities and rolls all of their tables —
  a press, so every table rolls whether or not it is marked to reroll, the same rule the per-shelf button
  follows. Setting a shop up means filling all of it, and doing that a shelf at a time is the sort of chore a
  GM does once and then stops using the feature.

  **Confirmed, unlike the per-shelf button and unlike removing a row.** It touches the whole shop at once,
  rolls every table on it, and cannot be undone by dragging one thing back — the scale is what makes it worth
  a question, and the dialog says that rolled stock is added rather than replaced. It reports one total
  rather than one notification per shelf.
- **Hovering an item shows dnd5e's own card** (`scripts/window-shop.js`): on the shelves and on both sides of
  the slate. The system already renders one and renders it right — `richTooltip()` knows what belongs on a
  weapon and what belongs on a potion, and keeps knowing when dnd5e changes its mind. Three dataset
  attributes are the whole integration; Squire does it the same way for the same reason.

  On the **name**, not the row: a row also carries a quantity cell saying how to edit it and buttons saying
  what they do, and a row-wide card would cover every one of them. The two sides of the slate resolve against
  different Actors — what you are buying is the merchant's, what you are selling is yours. Falls back to the
  plain name where `richTooltip` is absent, which a truncated row needs whatever else is missing.
- **Both windows remember where you put them** (`scripts/window-shop.js`,
  `scripts/window-merchant-config.js`): they were opting out of the window base's position memory, so a shop
  dragged and resized reset on the next open.

  `api-window.md` recommends opting out for multi-instance tools, because siblings sharing a position key
  overwrite each other's. We had taken the recommendation without the reasoning behind it: both windows
  already declare a **shared** key deliberately — a shop is a shop wherever it is opened. Two shops open at
  once now stack, which is rare and one drag apart; every shop resetting was every time.
- **Switching character has its own icon**: it was a circular arrow, which is what Refresh and Restock are.
  It is a person now, because it is about who rather than about repeating.
- **The slate's sums show the purse and which way each moves it** (`templates/window-shop.hbs`): a **Funds**
  row above the rest, carrying what the shopper holds — a total is a change to something, and it means little
  without the number it acts on. **Buying** is signed −, **Selling** +, because that is the direction each
  moves that purse. The **Total** is bold, red when the purse goes down and green when it goes up.

### Notes
- **Every stock policy delivers with `grantItem`, never `transferItem`.** The merchant's item is a template carrying a count, so a sale copies it and adjusts a number. That kept infinite stock free of races entirely, and it is what lets finite stock keep a sold-out row on the shelf. What finite stock does reintroduce is the read-then-write race, which the per-merchant lock answers.
- `"socket": true` from the first commit. Foundry reads manifests at world launch, so adding it later costs a world restart and silently drops every emit until then.
